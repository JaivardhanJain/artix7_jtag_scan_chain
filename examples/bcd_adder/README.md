# BCD adder (lab 4)

A two-digit BCD adder: two 4-bit decimal operands in, a 4-bit decimal digit
plus a carry out. Purely combinational, structural down to gate level.

| | |
|---|---|
| Widths | 8 in / 5 out |
| Vectors | 100 — every valid BCD operand pair |
| Wrapper | Generated by `scripts/new_lab.py` |
| Sources | **Not published** — coursework, see below |

```
python scripts\new_lab.py examples\bcd_adder\BCDAdder.vhdl --patch-toplevel
.\scripts\build.bat examples\bcd_adder
.\scripts\program.bat
python host\scanchain.py -t examples\bcd_adder\TRACEFILE.txt -o bcd.txt
```

## Why this example matters more than the others

It is the only **blind** test of `scripts/new_lab.py` in the repository.

The other reference wrappers are not independent evidence. `seq1011` was
written for this repository, `alu`'s wrapper was produced by the generator
itself, and `string_detector`'s was written by the same author who later
derived the generator's layout convention *from* it. Each of those checks the
generator against something it is related to.

This wrapper was written by someone else, for a design the generator had never
seen, before the generator existed. Running `new_lab.py` on `BCDAdder.vhdl`
produces the same bit layout the lab's author chose by hand:

```
A => input_vector(7 downto 4)
B => input_vector(3 downto 0)
Y => output_vector
```

That is the first real evidence that the convention `new_lab.py` implements is
the convention people actually use, rather than one reverse-engineered from a
sample of one and then confirmed against itself.

### The one thing it did differently

The generator writes `output_vector(4 downto 0)`; the lab's author wrote the
bare `output_vector`. Identical signals, different notation. `test_new_lab.py`
originally compared the two textually and reported a difference — so the fix
was to normalise full-width slices before comparing, not to change either
file. A test that fails on notation rather than meaning trains you to ignore
it.

### A parsing case neither other example covers

```vhdl
port(A, B : in std_logic_vector(3 downto 0);
```

Two ports sharing one declaration. `seq1011` declares scalars one per line and
`alu` declares vectors one per line, so this syntax had never been exercised
against a real design.

## Coverage, stated honestly

The 100 vectors are exhaustive over **valid BCD** — every pair where both
operands are 0–9. They are not exhaustive over the input space: 156 of the 256
possible 8-bit inputs have an operand above 9 and are never applied.

That is a defensible choice, since the adder's behaviour on non-BCD input is
not specified by the lab. It does mean a passing run says nothing about what
the design does when fed 1010–1111.

The expected-output column was checked against an independent Python model of
BCD addition before any hardware run: **100 vectors, 0 mismatches.** So a
hardware failure here can be attributed to the harness or the design, not to a
bad tracefile.

## Why the sources are not committed

They are filled-in solutions to a lab that may still be assigned. The wrapper,
the tracefile and this README are committed; the five design files are listed
explicitly in `.gitignore`. Drop them into this folder and it builds.

`examples/seq1011` exists so a fresh clone still has a complete example.
